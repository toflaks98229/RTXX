# 전투가 성립하지 않던 원인 세 가지

> 계기: 리팩토링 로드맵 1순위 "피해 전달 경로 실태 계측"
> 검증: `Mass_Battle_Runner` 배치 실행 (9,600명 / 60부대 / 701틱 / seed 12345)

## 0. 요약

로드맵은 "피해가 targetArmy 하나에서만 들어온다"를 1순위로 지목했습니다.
그것은 사실이었지만, **계측을 실제로 돌려 보니 그보다 앞선 문제가 둘 더 있었습니다.**

| 조치 | 사망 | 명중 성립 | LookRotation 오류 | simTotalMs |
|---|---|---|---|---|
| 기준선 | 2명 | 423회 | 20,496회 | 15.54 |
| ① 행군 방향 버그 수정 | 1명 | 1,426회 | 3회 | 13.49 |
| ② 피해 경로 + 패주 피격 | **63명** | **4,626회** | 0회 | 13.26 |

세 문제 모두 **예외를 내지 않고 조용히 틀리는** 종류였습니다.
그래서 "전투가 안 붙는다"는 증상만 보였고, 원인은 세 곳에 흩어져 있었습니다.

## 1. 부대가 명령한 곳이 아니라 월드 +Z로 행군했다

### 증상

701틱 동안 `Look rotation viewing vector is zero` 오류가 **20,496회**.
이동 중인 부대(26개) × 틱 수와 거의 정확히 일치합니다. 즉 **이동 중인 모든
부대가 매 틱** 걸리고 있었습니다.

### 원인

```csharp
// Army_Move.Rotation()  (수정 전)
Vector3 direction = navMeshAgent.steeringTarget - formation_Move_Transform.position;
Quaternion lookRotation = Quaternion.LookRotation(direction, Vector3.up);
```

이 부대의 `NavMeshAgent`는 `_Start()`에서 `isStopped = true`로 세워 둡니다.
경로를 따라 걷게 하지 않고 `Move()`가 직접 밀기 때문입니다.

그런데 **멈춰 선 에이전트의 `steeringTarget`은 자기 위치 그대로**입니다.
따라서 `direction`이 언제나 영벡터가 되고,

1. `LookRotation`이 오류를 내며 **항등 회전**을 돌려주고
2. `RotateTowards`가 부대를 월드 정면(+Z)으로 서서히 돌리고
3. `Move()`는 그 `forward` 방향으로 전진하므로

**부대가 명령한 곳이 아니라 +Z로 행군했습니다.** 60개 부대가 서로 만나지
못한 이유이고, 그래서 사망자가 701틱에 2명이었습니다.

같은 이유로 `Move()`의 진형 이동 분기도 망가져 있었습니다.
`remainingDistance`가 0으로 굳어 **진형 이동에 들어가는 즉시 `Move_Stop()`** 이
걸렸습니다.

### 수정

방향을 에이전트가 아니라 `locationMoveTo`(명령이 확정한 목적지)에서 직접
구합니다. 에이전트 상태와 무관하게 언제나 유효합니다.

## 2. 피해가 'targetArmy 하나'에서만 들어왔다

### 계측

계측기에 두 값을 추가했습니다.

- `attacksLanded` : `Attack_End`가 사거리를 다시 재고 `bhitTarget`을 세운 횟수
- `damageApplied` : 실제로 HP가 깎인 유닛 수

```
명중 성립 : 1,426회
피격 유닛 :   228명     <- 명중의 16%
막힌 공격자: 틱당 2.76개 부대  (몸을 맞대고도 피해를 못 주는 부대)
```

### 원인

피해가 들어오는 경로는 전수 조사 결과 둘뿐이고, 둘 다 `targetArmy`에
게이트되어 있었습니다.

```csharp
List<Unit> targetUnits = targetArmy.GetUnits();   // 공격자 후보는 이 부대뿐
unit_Fight_Job.target_Unit_Datas = targetDatas;
```

`Unit_Fight_Job`은 **자기 부대 유닛이 맞는 피해**를 계산합니다. 그런데 공격자
후보가 `targetArmy` 소속으로 한정되어 있어, **나를 때리는 부대가 내 표적이
아니면 그 타격은 명중 판정까지 끝난 뒤 아무도 읽지 않고 사라졌습니다.**

특히 `_Update_Target_Army()`는 "이미 근접 교전 중이면 표적을 바꾸지 않는다"고
명시합니다. 정면에 붙들린 부대는 측면 기습자로 표적을 **영영 바꾸지 않을 수**
있었습니다. 이 게임의 정체성이 "측후방이 방어를 무력화한다"인데
(`hit_Angle_Back`에서 방어력·방패가 0), 그 공격의 전달 경로 자체가 막혀
있었습니다.

사기 쪽은 정반대를 가정합니다.

```csharp
if (enemyArmies > 1)
    modifiers.surrounded = -(enemyArmies - 1) * Constant.morale_Penalty_Surrounded;
```

즉 **사기는 포위를 정확히 세는데 체력만 줄지 않는** 상태였습니다.

### 수정

`Collect_Fight_Armies()`가 표적 부대와 **탐지된 모든 적 부대**를 피해원으로
모읍니다. 여러 부대의 유닛이 한 배열에 섞이므로, 공격자의 부대 스탯은
`Unit_Data.armyIndex`로 `NativeArray<Army_Data>`에서 찾습니다.

셀 크기는 그 부대들 전부의 최대 사거리로 잡습니다. 하나라도 짧게 잡으면
그 부대의 공격이 3×3 탐색에서 누락됩니다.

Controller는 **전처리가 끝난 뒤** 부대 스탯 스냅샷을 갱신해 넘깁니다.
그러지 않으면 공격자만 지형(고지 우위) 보정을 못 받아 좌우가 어긋납니다.

## 3. 패주하는 부대는 아무에게도 맞지 않았다

### 원인

```csharp
void _Update_Target()
{
    if (army_Data.IsBroken())
    {
        targetArmy = null;
        army_Data.e_Army_Fight = E_Army_Fight.Non;
        return;                    // ← 여기
    }
    ...
    _Update_Target_Unit();         // 이 Job이 '내가 맞는 피해'를 계산한다
}
```

이 조기 반환은 "무너진 부대는 싸우지 않는다"는 뜻으로 쓰였지만, 실제 효과는
**"무너진 부대는 아무에게도 맞지 않는다"** 였습니다.
`_Update_Target_Unit`이 거는 Job은 내가 때리는 계산이 아니라 **내가 맞는**
계산이기 때문입니다.

패주하는 적을 베는 것은 이 장르에서 사상자가 가장 많이 나오는 국면입니다.
그 국면이 통째로 무효였습니다.

### 수정

무너진 부대도 Job을 겁니다. 대신 `bcanAcquireTarget = false`로 넘겨
**표적 획득만 막고 피격은 그대로 둡니다.** 패주 중에는 반격하지 않지만
베이기는 합니다.

## 4. 회귀 감시

지표 하나를 남겼습니다.

```
피해원 누락 : 0개 (정상: 접촉한 적은 모두 피해를 줄 수 있음)
```

몸을 맞댄 적 부대 수와, 그중 실제로 피해를 줄 수 있는 부대 수를 비교합니다.
**언제나 0이어야 합니다.** 0이 아니게 되는 순간 피해 경로가 어딘가에서 다시
좁아졌다는 뜻입니다.

판정은 `Army_Fight.Is_Damage_Source()` 한 곳에만 적혀 있습니다.
피해원을 모으는 쪽과 누락을 검사하는 쪽이 같은 것을 보게 하기 위함입니다.
두 곳에 조건을 따로 적으면 한쪽만 좁아져도 지표가 0으로 남아 아무도
눈치채지 못합니다.

### 지표 해석 주의

`피격 유닛`은 피해 '건수'가 아닙니다. `Unit_Data.bgetDamage`는 bool 하나이고
`Unit._Update_Fight`가 틱마다 한 번만 소비하므로, 한 유닛이 같은 틱에 세
명에게 맞아도 1로 셉니다. 난전이 격해질수록 더 크게 과소 집계됩니다.

따라서 `피격 유닛 / 명중 성립` 비율을 '피해 전달률'로 읽으면 안 됩니다.
그 비율에는 명중 굴림(`hit_Chance`)과 위 합산 손실이 함께 섞여 있습니다.
피해가 실제로 전달되는지는 **`피해원 누락`(0이어야 함)과 사망자 수**로
판단하십시오.

## 5. 전투가 돌기 시작하자 드러난 것

701틱으로는 사기 붕괴가 한 번도 일어나지 않아 판단이 어려웠습니다.
2,000틱으로 늘리자 전투가 끝까지 흘렀습니다.

```
사망 1,717명 / 붕괴 40회 / 돌격 17회 / 생존 7,883명
피해원 누락 0 · 좌표/인덱스 이상 0 · LookRotation 오류 0
```

**붕괴가 처음으로 발생했습니다.** 지금까지 아무도 죽지 않았으므로 사기가
떨어질 일이 없었고, 그래서 `Move_Escape` 경로는 실행된 적이 없었습니다.

그러자 검증기가 곧바로 잡아냈습니다.

```
[문제] 틱 1130: 패주 부대의 기준점이 지면에서 9.7m 벗어났습니다.
```

`Clamp_Pivot_To_NavMesh`는 '내브메시를 벗어났는가'만 봅니다. 그런데 내브메시
표면은 지형과 높이가 다를 수 있어(경사·단차), 내브메시 위에 잘 있어도
기준점이 지형에서 뜹니다. 기준점이 뜨면 진형 슬롯도 함께 뜨고, 유닛은 닿을
수 없는 자리를 향해 달립니다.

`Move_Stop`이 같은 이유로 이미 지면 스냅을 하고 있었으므로, `Move_Escape`에도
같은 처리를 넣었습니다.

> 이것이 이 세션의 교훈입니다. **버그는 그 코드가 실행될 때까지 발견되지
> 않습니다.** 전투가 성립하지 않는 동안에는 사기·패주·추격 경로 전체가
> 죽은 코드였고, 그 안의 결함은 아무도 볼 수 없었습니다.

## 6. 남은 것

- **밸런스는 아직 검증된 적이 없습니다.** 지금까지 전투가 성립하지 않았으므로,
  `Balance_Data`의 122개 수치는 전부 '전투가 도는 상태'에서 조정된 적이
  없습니다. 사망 63명(701틱)이 적정한지도 아직 판단 근거가 없습니다.
  더 긴 실행(2,000틱 이상)으로 전투가 끝까지 흐르는지 먼저 봐야 합니다.

- **원거리 비대칭**: `_Update_Detection`은 *내* 사거리로만 적을 등록합니다.
  나보다 사거리가 긴 적이 내 탐지 밖에서 쏘면 그 피해는 여전히 전달되지
  않습니다. 접촉 교전이 지배적인 현재 구성에서는 드러나지 않았지만,
  궁병 비중을 늘리면 다시 문제가 됩니다.

- **성능 기준선이 새로 필요합니다.** 지금까지의 성능 수치는 전부 '전투가
  돌지 않는 상태'에서 잰 것이었습니다. 실제로 싸우기 시작하자
  2,000틱 평균 20.31 ms(60fps 예산의 122%), 스파이크 46.7%가 나옵니다.
  기준선 19.39 ms와 비슷해 보이지만 **하는 일의 양이 전혀 다릅니다.**

  즉 Architecture_Report_v2의 3-3절이 지목한 최적화 대상(Prepare 하위 계측,
  `_Update_Terrain`의 동기 레이캐스트, Battle_AI의 O(N²))은 이제야
  **의미 있는 부하 위에서** 측정할 수 있게 되었습니다.
  그전까지의 최적화 판단은 빈 전장에서 내려진 것입니다.
