# 태세별 밀집도 + 적진 관통 방지 — 조사 및 설계

> 요청: (1) 태세에 따라 유닛 배치 밀집도를 다르게, (2) 적과 충돌 시
> 안쪽으로 파고드는 것을 막을 것
> 기준 게임: Total War 시리즈, 특히 Three Kingdoms

---

## 1. 조사 — 토탈워의 밀집도 설계

### 1-1. Loose(산개)는 '면적'과 '돌격 저항'을 맞바꿉니다

Three Kingdoms의 Loose formation은 병사 간격을 넓혀 **유닛의 물리적
점유 면적을 키웁니다.** 그 대가로:

| 얻는 것 | 잃는 것 |
|---|---|
| 화살에 맞기 어려움 (밀도가 낮아짐) | **돌격 저항(charge resistance) 크게 감소** |

핵심은 밀도가 곧 방어라는 점입니다. 흩어지면 화살은 피하지만 기병
돌격에는 종잇장이 됩니다.

### 1-2. 반대편 — Turtle/방패벽은 밀집으로 버팁니다

Turtle formation은 방패를 겹쳐 거의 이음매 없는 방벽을 만듭니다.
돌격 저항과 특히 원거리 저항이 크게 오르고, 대신 **걷기 속도로 제한**
되며 근접 공격 속도가 떨어집니다.

Circle formation은 밀집 원형으로 서서 측후면을 없앱니다.

### 1-3. 정리하면 밀집도는 삼각 거래입니다

```
        밀집 (간격 좁음)          산개 (간격 넓음)
원거리    잘 맞음 (나쁨)           잘 안 맞음 (좋음)
돌격      잘 버팀 (좋음)           무너짐 (나쁨)
기동      느림                     빠름
```

이 프로젝트에는 이미 세 축이 전부 구현되어 있습니다
(`stance_ShieldWall_Range_Defence`, `stance_*_Charge_Resist`,
`stance_Wall_Speed_Rate`). **없는 것은 '눈에 보이는 간격'뿐입니다.**

즉 수치로는 이미 밀집한 것처럼 계산하면서 화면에서는 늘 같은 간격으로
서 있었습니다. 이번 작업은 그 불일치를 없앱니다.

## 2. 설계 — 태세별 간격 배율

### 2-1. 값

`Army_Data.GetInterval()`에 태세 배율을 곱합니다. 기존 호출부가 전부
이 함수를 거치므로 진형 계산·재정비·마커가 한꺼번에 따라옵니다.

| 태세 | 배율 | 근거 |
|---|---|---|
| Line (전열) | 1.00 | 기준 |
| Loose (느슨) | **1.35** | 토탈워 Loose. 면적을 넓혀 화살 회피 |
| ShieldWall | **0.75** | 방패를 겹치는 밀집 |
| SpearWall | **0.80** | 창을 겨누는 밀집. 방패벽보다는 덜 조임 |
| Skirmish (산개) | **1.50** | 가장 흩어짐. 궁병 운용 |

배율만 두고 절대값을 두지 않는 이유: 병종마다 `interval`이 다릅니다
(기병이 보병보다 넓습니다). 배율이어야 그 차이가 유지됩니다.

### 2-2. 하한

간격이 유닛 반지름의 2배보다 작아지면 병사들이 서로 겹칩니다.
충돌 해소가 매 틱 밀어내므로 대열이 진동합니다. 그래서 다음을 지킵니다.

```
최종 간격 = max(간격 * 배율, 반지름 * 2 * 1.05)
```

방패벽 0.75가 이 하한에 걸리면 자동으로 하한이 적용됩니다.

## 3. 조사 — 적진 관통 문제

### 3-1. 토탈워도 같은 문제를 겪었습니다

Total War: Arena 패치 10 이전에는 **클릭을 연타하면 아군이 적진을
'뚫고 지나가(pulled through)' 교전에서 빠져나올 수 있었습니다.**
의도된 설계가 아니었고, CA는 **'소프트 충돌(soft collision)'** 을
추가해 막았습니다.

또 하나 확인된 것: 질량이 큰 몬스터는 **대열을 뚫고 들어가 후방에서
날뛸 수 있습니다.** 즉 관통은 완전히 금지된 것이 아니라 **질량에
비례해 허용**됩니다.

### 3-2. 현재 구현의 문제

`Collision_Resolve_Job`은 아군과 적군을 **똑같이** 처리합니다.

```csharp
float share = total > 0.0001f ? you.mass / total : 0.5f;
push += dir * (overlap * share * separationRate);

if (you.bplayer != me.bplayer) { /* 접촉 기록만 */ }
```

적/아군 구분은 `benemyContact` 기록에만 쓰이고, **밀어내는 힘은 같습니다.**
그래서 한 틱에 밀려나는 양(`maxSeparationPerTick = 0.35`)을 넘어서는
전진 명령이 들어오면 적 사이를 비집고 들어갑니다.

## 4. 설계 — 관통 방지

사용자 제안("적/아군이 걸리는 충돌체를 다르게")을 따르되, 별도 콜라이더
레이어를 만들지 않고 **같은 그리드 안에서 계수를 다르게** 둡니다.
콜라이더를 나누면 순회를 두 번 해야 해서 9,600 유닛에서 비용이 두 배가
됩니다.

### 4-1. 적과 아군의 분리 강도를 다르게

```
아군끼리 : separationRate 그대로 (0.5)  — 대열이 자연스럽게 정돈됨
적과     : separationRate * 2.0        — 강하게 튕겨냄
```

적을 더 세게 밀어내면 겹침이 빨리 해소되어 파고들 틈이 줄어듭니다.

### 4-2. 적에 대해서는 '반지름'을 키웁니다

접촉 판정에 쓰는 반지름을 적 상대로만 키우면, **닿기 전에 먼저 멈춥니다.**
이것이 사용자가 말한 '충돌체를 다르게'의 실질입니다.

```
아군 판정 반지름 : radius
적군 판정 반지름 : radius * 1.25
```

### 4-3. 전진 성분 제거 (핵심)

가장 중요한 것은 **적 쪽으로 파고드는 이동 성분 자체를 없애는 것**입니다.
이미 `Block_Into_Enemy()`가 그 일을 하고 있으므로, 관통이 남는다면
그 강도가 부족한 것입니다.

```
접촉 중이면 : 적 방향 이동 성분 * (1 - blockRate)
```

`blockRate = 1.0`이면 완전 차단입니다.

### 4-4. 질량 예외 — 토탈워를 따릅니다

질량이 훨씬 큰 유닛(기병·대형)은 **뚫고 들어갈 수 있어야** 합니다.
그것이 돌격의 의미입니다. 그래서 차단을 무조건 걸지 않고 질량비로
완화합니다.

```
질량비 = 내 질량 / 상대 질량
질량비가 임계(2.0) 이상이면 차단을 절반만 적용
```

이렇게 하면 보병은 서로 밀리지만 기병 돌격은 대열을 헤집습니다.

## 5. 위험

| 위험 | 대응 |
|---|---|
| 간격이 좁아지면 충돌 해소가 진동 | 반지름 기반 하한을 강제 |
| 적 분리를 세게 하면 서로 튕겨 교전이 끊김 | 상한(`maxSeparationPerTick`)이 이미 존재 |
| 태세 변경 시 대열이 갑자기 벌어짐 | 이미 재정비가 걸리므로 자연스럽게 이동 |
| 결정론 깨짐 | 모든 계수는 `Balance_Data`에 두고 Job 안에서 읽음 |

## 6. 진행 순서

```
1) 간격 배율     — 눈에 바로 보이고 되돌리기 쉬움
2) 적 분리 강화  — 관통 완화
3) 질량 예외     — 기병 돌격이 죽지 않도록
```

각 단계마다 대규모 전투로 계측해 프레임 영향을 확인합니다.

## 7. 구현 결과

### 7-1. 만든 것

| 위치 | 내용 |
|---|---|
| `Balance_Data` | `density_*` 5종 + 하한, `collide_*` 4종 |
| `Army_Data.GetInterval()` | 태세 배율과 하한을 적용 |
| `Army_Data.GetDensityRate()` | 태세 -> 배율 |
| `Collision_Grid_Build_Job` | 조밀 진영 배열(`sides`) 출력 추가 |
| `Collision_Resolve_Job` | 적/아군 분리 계수 분리 + 질량 예외 |
| `Editor/Density_Probe.cs` | 태세별 간격 검증 |

`GetInterval()` 한 곳에 배율을 걸었습니다. 진형 계산·재정비·슬롯
마커가 전부 이 함수를 거치므로, 태세를 바꾸면 대열 폭·열 수·마커가
한꺼번에 따라옵니다.

### 7-2. 검증 — 간격

    [밀집도] Infantry  기본간격 1.00  반지름 0.30  하한 0.63
        Line        배율 1.00  의도 1.00  실제 1.00
        Loose       배율 1.35  의도 1.35  실제 1.35
        ShieldWall  배율 0.75  의도 0.75  실제 0.75
        SpearWall   배율 0.85  의도 0.85  실제 0.85
        Skirmish    배율 1.50  의도 1.50  실제 1.50

다섯 태세 모두 의도한 값이 나오고 **하한(0.63)에 걸린 태세가
없습니다.** 방패벽 0.75가 하한 위이므로 실제로 조여집니다.

도구: **RTXX > 검증: 태세별 밀집도**

### 7-3. 검증 — 성능

9,600 유닛 600틱 계측입니다.

| 단계 | 평균(ms) | 비중 |
|---|---|---|
| Prepare | 9.02 | 47.0% |
| Apply | 3.02 | 15.7% |
| TransformWrite | 2.53 | 13.2% |
| **Collision** | **0.58** | **3.0%** |

충돌은 3%입니다. `sides` 배열을 추가했지만 bool 1바이트라 캐시 라인
하나에 64개가 들어와 비용이 사실상 늘지 않았습니다.

콜라이더 레이어를 나누지 않은 판단이 여기서 확인됩니다. 나눴다면
격자를 두 번 순회해 이 3%가 6%가 됐을 것입니다.

### 7-4. 별개로 발견한 것 — 사상자 0

계측에서 `deaths=0 / charges=6`이 나왔습니다. 부대가 만나 돌격까지
했는데 아무도 죽지 않습니다.

**이번 변경 때문이 아닙니다.** `collide_Enemy_Radius_Rate`를 1.0으로
되돌려(즉 적 반지름 확대를 끄고) 다시 재도 `deaths=0`이었습니다.
이전부터 있던 별도 문제입니다.

`Prepare`가 47%를 쓰는 것과 함께 따로 조사할 항목입니다.

## 8. 배치 단계 즉시 재배치

### 8-1. 왜 필요했나

밀집도를 넣었는데 화면에서 아무 일도 일어나지 않는다는 보고가
있었습니다. 원인이 두 개였습니다.

**(1) 슬롯을 다시 만들지 않았습니다.**
`Set_Stance`가 재정비를 요청하긴 했지만, 재정비(`Move_Reformation`)는
**이미 만들어진 슬롯**에 자리를 배정할 뿐입니다. 간격이 바뀌었으면
슬롯 자체를 다시 만들어야 합니다.

`Rebuild_Formation_For_Stance()`를 추가했습니다. 전열의 방향과 길이는
그대로 두고 간격만 바꾸므로, 폭은 유지된 채 밀집도만 달라집니다.

**(2) 배치 중에는 움직여 줄 주체가 없습니다.**
`Controller.FixedUpdate`는 배치 단계면 시뮬레이션 틱을 통째로
건너뜁니다. 그래서 목적지를 정해 놓아도 아무도 실행하지 않습니다.

### 8-2. 즉시 배치 경로

배치 중일 때만 `Snap_Units_To_Slots()`로 순간이동시킵니다.

| 상황 | 동작 |
|---|---|
| 배치 단계 | 즉시 순간이동 |
| 교전 중 | 재정비 예약 (걸어서 이동) |

**교전 중에 순간이동하면 안 됩니다.** 대열이 갑자기 재배치되면 적과의
접촉이 끊기고 돌격 판정이 무너집니다.

적용 지점은 두 곳입니다.

    Army.Set_Stance()            태세 변경 시
    Army_Move.Move_Start_Internal()  이동 명령 시 (모든 명령이 여기를 거침)

이동 명령 쪽은 `e_Army_Move`를 `Idle`로 되돌립니다. 그러지 않으면
전투가 시작될 때 '아직 이동 중'으로 판정되어 이미 도착한 자리를 향해
다시 걸어갑니다.

### 8-3. 배치 여부를 어떻게 아는가

`Army`는 `Battle_Manager`를 참조하지 않습니다. 부대가 전투 진행
계층을 몰라도 되는 것이 이 프로젝트의 구조이고, 참조를 새로 배선하면
프리팹과 씬을 전부 고쳐야 합니다.

그래서 `Battle_Manager.bdeploying` 정적 속성을 두었습니다. bool
하나뿐이고 `Battle_Manager`가 유일한 주인이므로 가장 싸고 안전합니다.

**기본값이 false인 것에 주의하십시오.** `Battle_Manager`가 없는
씬(`Scene_MassBattle` 등)에서는 배치 개념이 없으므로 기존 경로가
그대로 동작합니다. 실제로 대규모 전투 계측에서 확인했습니다.

### 8-4. 회귀 확인

`Scene_MassBattle` 600틱 계측 (Battle_Manager 없음 = 배치 아님):

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| simTotalMs | 19.17 | 16.82 |
| spikes | 402 | 107 |
| alive | 9600 | 9600 |

즉시 배치 경로를 타지 않았고, 대규모 전투 동작도 정상입니다.

## 9. 정정 — 진형 기준점이 중심이 아니라 끝점이었습니다

보고된 두 증상의 원인이 하나였습니다.

- 전투 중 태세를 바꿔도 그 진형으로 재배치되지 않음
- 태세 버튼을 누를 때마다 대열이 **옆으로 밀려남**

### 9-1. 넣는 값과 나오는 값의 의미가 다릅니다

`Formation_Data.position`의 주석은 '진형의 중심 위치'입니다. 그런데
실제로 저장되는 값은 다릅니다.

```csharp
// Set_Formation_Internal 끝
return new Formation_Data(num_width, add_width, vector3s[0], vector3s);
//                                              ^^^^^^^^^^^ 첫 슬롯
```

반면 같은 함수의 입력은 중심처럼 다뤄집니다.

```csharp
formation_Start = position + add_width * num_width * 0.5f;
```

즉 **입력은 중심, 출력은 끝점**입니다. 나온 값을 그대로 다시 넣으면
매번 절반 폭씩 한쪽으로 나아갑니다. 태세 버튼을 누를 때마다 대열이
옆으로 가던 것이 이것입니다.

`Get_Formation_Anchor()`를 추가해 그 변환을 되돌립니다.

```csharp
anchor = formation_Data.position
         - formation_Data.direction * formation_Data.num * 0.5f;
```

`direction`에는 `add_width`(축 × 간격)가 들어 있으므로 **진형을 만들
당시의 간격으로 정확히 역산**됩니다.

### 9-2. 가로 인원 수를 유지합니다

예전에는 `Set_Formation(Formation_Data)`를 써서 **길이(m)** 를 유지하고
열 수를 다시 계산했습니다. 그러면 밀집해도 대열 폭이 그대로입니다.

이제 **가로 인원 수**를 유지하고 길이가 바뀌게 했습니다. 밀집하면
좁아지고 흩어지면 넓어집니다. 토탈워의 Loose가 '유닛의 점유 면적을
넓히는' 것과 같은 동작입니다.

### 9-3. 전투 중에는 예약이 아니라 직접 명령합니다

재정비 예약(`breformation`)은 **대기 상태에서만** 소비됩니다. 그런데
전투 중에는 부대가 이동·돌격·패주 상태일 수 있고, 그러면
`Army_Data._Update`의 `default:` 분기가 예약을 도로 내립니다.

그래서 태세를 바꿔도 대열이 그대로였습니다. 이제 슬롯을 새로 만든 뒤
`Reform_To_Current_Formation()`으로 직접 지시합니다.

| 상황 | 동작 |
|---|---|
| 배치 단계 | `Snap_Units_To_Slots` (순간이동) |
| 그 외 | `Reform_To_Current_Formation` (걸어서 이동) |

교전 중 순간이동은 여전히 금지입니다. 접촉이 끊기고 돌격 판정이
무너집니다.

### 9-4. 기준을 '부대 위치 = 중심'으로 통일

앵커를 역산하는 방식은 동작하지만, 여전히 '입력 position'과 '저장된
position'의 뜻이 다르다는 사실을 호출부가 알아야 합니다. 그래서
기준을 하나로 고정했습니다.

**진형은 언제나 부대 위치를 한가운데로 삼아 만듭니다.**

`Set_Formation_At_Center(num, axis, center)`를 추가했습니다. 좌표 규약
변환을 안으로 숨기므로 호출부는 중심만 넘기면 됩니다.

```csharp
Set_Formation_At_Center(formation_Data.num,
                        formation_Data.direction,
                        GetPosition());     // 부대 위치 = 중심
```

Formation_Job이 `formation_Start`를 기준으로 좌우 번갈아 슬롯을 펼치므로
**`formation_Start`가 곧 열의 한가운데**입니다. 그런데 입력 position은
거기서 절반 폭만큼 떨어진 값이라, 그 차이를 함수 안에서 미리 빼 둡니다.

부대 위치는 병사들의 중심이므로 '지금 있는 자리에서 대열만 다시
정렬한다'는 뜻이 되어 직관과도 맞고, 몇 번을 다시 만들어도 같은
자리에 모입니다.

### 9-5. 검증

`Stance_Rebuild_Probe`에 왕복 검사를 넣었습니다. 태세를 5회 왕복한 뒤
대열 중심이 제자리인지 잽니다. 밀려나는 버그가 있으면 왕복할수록
멀어지므로 확실히 드러납니다.

도구: **RTXX > 검증: 태세 전환 시 진형 재구성** (플레이 중 실행)

대규모 전투 회귀는 정상입니다(`alive=9600`, 크래시 없음).
