# 무기·방패 손 위치 어긋남 — crawl 원본 조사 결과

> 질문: 일부 유닛 스프라이트의 손 위치와 hand 아이템 위치가 맞지 않는다.
> 그 이유를 crawl 저장소에서 찾을 것.
> 조사 대상: `External/crawl/crawl-ref/source` (stone_soup-0.34)

---

## 0. 결론

**DCSS는 무기·방패 위치를 타일마다 픽셀 단위로 보정하는 표를 코드에
갖고 있습니다.** 타일 그림만 겹쳐서는 손에 맞지 않습니다.

    tilemcache.cc
      mcache_monster::get_weapon_offset()   무기 오프셋 337종
      mcache_monster::get_shield_offset()   방패 오프셋 160종

원본 주석이 그대로 말해 줍니다.

> Returns the amount of pixels necessary to shift a wielded weapon
> from its default placement.
> (기본 배치에서 무기를 옮기는 데 필요한 픽셀 양을 반환한다)

무기 오프셋 337종 중 **312종이 0이 아닙니다.** 즉 대부분의 몬스터
타일은 보정 없이 무기를 겹치면 어긋나는 것이 정상입니다.

이전에 제가 "DCSS 타일은 무기가 캔버스 제자리에 그려져 있어 오프셋
데이터가 필요 없다"고 적었던 것은 **틀렸습니다.** 그 설명은 플레이어
인형(doll)의 기본 경로에만 해당하고, 몬스터 타일에는 해당하지 않습니다.

---

## 1. 이 프로젝트가 쓰는 타일의 실제 보정값

`tilemcache.cc`에서 추출했습니다. 단위는 픽셀이며 32x32 타일 기준입니다.

| 타일 | 무기 (x, y) | 방패 (x, y) |
|---|---|---|
| `HUMAN`, `HUMAN_1`, `HUMAN_2` | **(-1, -2)** | (0, 0) |
| `ORC` | **(-2, -1)** | (1, 0) |
| `ORC_WARRIOR` | **(-2, -1)** | (1, 0) |
| `ORC_KNIGHT` | **(-2, +1)** | (1, 0) |
| `ORC_PRIEST` | **(-1, +1)** | (1, 0) |
| `ORC_WARLORD` | **(-3, 0)** | (1, 0) |

여기서 두 가지가 보입니다.

1. **몸통마다 값이 다릅니다.** 그래서 "어떤 유닛은 맞고 어떤 유닛은
   어긋난다"가 됩니다. 지금 이 프로젝트는 몸통을 무작위로 고르므로
   (`Unit._Start`의 `images_Unit[Random.Range(...)]`) 같은 부대 안에서도
   맞는 병사와 어긋난 병사가 섞입니다. **보고하신 증상과 정확히
   일치합니다.**

2. **오크는 무기가 왼쪽으로 2px, 인간은 1px입니다.** 32px 타일에서
   2px는 유닛 크기의 6%이고, 손 하나 폭입니다.

---

## 2. 왜 DCSS는 이런 표를 따로 두는가

타일 원본이 **잘린 채로 저장되기 때문입니다.**

`rltiles/tool/tile_page.cc`:

```cpp
if (m_tiles[i]->shrink())
    m_tiles[i]->get_bounding_box(ofs_x, ofs_y, tilew, tileh);
else
{
    ofs_x = 0; ofs_y = 0;
    tilew = m_tiles[i]->width();
    ...
}
m_offsets.push_back(ofs_x);
m_offsets.push_back(ofs_y);
```

즉 DCSS의 빌드 도구는 타일의 투명 여백을 **잘라내고(shrink)**, 그
잘라낸 양을 **오프셋으로 따로 저장**합니다. 렌더러가 그리는 시점에
그 값을 도로 더해 원래 자리에 놓습니다.

`dc-player.txt`에는 `%shrink 0`이 한 번도 나오지 않습니다.
즉 **플레이어/장비 타일은 전부 잘려서 저장됩니다.**

### 우리가 Full Rect를 쓴 것이 맞는 이유

Unity에는 "잘라낸 양을 도로 더해 주는" 단계가 없습니다.
따라서 DCSS의 두 단계 중 앞쪽(자르기)만 흉내 내면 뒤쪽(복원)이
빠져 어긋납니다. 그것이 직전에 고친 Tight 메시 문제였습니다.

    Tight   = 자르기만 함, 복원 없음  -> 어긋남 (수정 전)
    FullRect = 자르지도 않음          -> 원본 좌표 유지 (수정 후)

**Full Rect 전환은 옳았고 유지해야 합니다.** 다만 그것으로 해결되는
것은 '트리밍에 의한 어긋남'까지이고, 아래의 '몸통별 손 위치 차이'는
남아 있습니다. 이 둘은 원인이 다른 별개의 문제입니다.

## 3. 적용 조건 — 주의할 점

이 오프셋은 **몬스터 타일 합성 경로에서만** 적용됩니다.

`tiledoll.cc:975`:

```cpp
int ofs_x = 0, ofs_y = 0;
if ((p == TILEP_PART_HAND1 && ...SLOT_WEAPON
     || p == TILEP_PART_HAND2 && ...SLOT_OFFHAND)
    && dind < draw_info_count - 1)
{
    ofs_x = dinfo[...].ofs_x;
    ofs_y = dinfo[...].ofs_y;
}
```

그리고 이 `dinfo`는 `player_uses_monster_tile()`일 때만 채워집니다.
일반 플레이어 인형은 `hand1/hand2` 파트가 몸통과 같은 규격으로
그려져 있어 보정이 0입니다.

**우리 프로젝트는 몬스터 타일(human, orc)에 hand 아이템을 얹는
구조이므로 몬스터 경로에 해당합니다.** 따라서 오프셋 표가 필요합니다.

## 4. 수정 방안

### 방안 A — 오프셋 표를 이식 (권장)

crawl의 표에서 우리가 쓰는 타일 6종만 가져옵니다.
스프라이트 이름으로 오프셋을 찾아 `Unit_Weapon` / `Unit_Shield`의
로컬 위치에 반영합니다.

    32px 타일, PPU 32 -> 1px = 0.03125 유닛
    HUMAN 무기 (-1, -2) -> 로컬 (-0.03125, -0.0625)

장점: 원본과 동일한 결과. 몸통을 추가해도 표만 늘리면 됩니다.
단점: 몸통 스프라이트별로 자식 Transform을 따로 잡아야 하므로
      `Unit._Start`에서 몸통을 고른 뒤 오프셋을 적용해야 합니다.

### 방안 B — 몸통을 한 종류로 고정

무작위 선택을 없애면 어긋남이 균일해지고, 그 하나만 맞추면 됩니다.
가장 싸지만 병사가 전부 같은 그림이 되어 난전의 시각적 다양성이
사라집니다.

### 방안 C — 그대로 둔다

1~2px입니다. 카메라가 멀면 보이지 않습니다.
다만 확대하면 눈에 띄고, 보고하신 것이 그 증상입니다.

## 5. 권고

**방안 A**를 권합니다. 데이터가 이미 원본에 있어 새로 만들 것이 없고,
표가 6줄이라 비용이 작습니다.

적용 지점은 `Unit._Start`입니다. 이미 그곳에서 몸통 스프라이트를
무작위로 고르고 있으므로, 고른 결과에 따라 무기·방패 자식의
`localPosition`을 지정하면 됩니다.

주의: 무기와 방패는 오프셋이 **서로 다릅니다**(오크는 무기 -2, 방패 +1).
한 값으로 둘 다 옮기면 한쪽이 여전히 틀어집니다.

## 6. 구현 결과 (방안 A 적용)

### 만든 것

| 파일 | 역할 |
|---|---|
| `Character/Unit/Unit_Hand_Offset.cs` | 몸통 이름 -> 무기·방패 보정표 |
| `Editor/Hand_Offset_Probe.cs` | 표가 씬의 몸통을 모두 덮는지 검증 |

`Unit._Start`가 몸통을 고른 **직후** `Unit_Hand_Offset.Apply`를 호출합니다.
몸통을 무작위로 고르므로 그 뒤여야 합니다.

```csharp
sprite_Unit.sprite = army.images_Unit[Random.Range(...)];

Unit_Hand_Offset.Apply(sprite_Unit.sprite, sprite_Weapon, sprite_Shield);
```

## 7. 정정 — 픽셀 오프셋만으로는 맞지 않습니다 (계층 차이)

6장의 첫 구현은 표의 픽셀 값을 두 렌더러에 **그대로** 넣었습니다.
그런데 사용자가 실제로 맞춰 본 값이 달랐습니다.

    무기가 대충 맞는 위치 = Vector3(-0.03125, 0.134, 0)

이 값을 분해하면 원인이 드러납니다.

| 성분 | 값 | 정체 |
|---|---|---|
| x | -0.03125 | **정확히 -1px.** 표의 HUMAN 무기 x와 일치 |
| y | 0.134 | 1px의 배수가 아님. `(size-1)*0.5` (size=1.268)와 정확히 일치 |

즉 **x는 맞았고 y는 타일 오프셋이 아니었습니다.**
y는 몸통이 위로 올라간 양이었습니다.

### 왜 이런 일이 생기는가

`Unit_Animation._Start`가 몸통(`Unit_Sprite`)에 두 가지를 겁니다.

```csharp
transform.localScale    = size;              // 크기 배율
transform.localPosition = (0, (size-1)*0.5, 0);  // 키만큼 들어올림
```

그런데 프리팹 실측 결과 두 장비의 부모가 **서로 다릅니다.**

    Unit_Weapon -> Unit_Sprite 의 자식   (몸통 아래)
    Unit_Shield -> Unit 의 자식          (몸통과 형제)

무기는 위 두 변환을 **물려받고**, 방패는 **전혀 받지 않습니다.**
같은 픽셀 값을 넣어도 결과가 갈리는 이유입니다.

### 수정한 계산

```
몸통의 자손이면 : 오프셋 / size
                  (부모가 size배이므로 나눠서 상쇄. 들어올림은 이미 받음)
그렇지 않으면   : 오프셋 * size + (size-1)*0.5
                  (아무것도 못 받으므로 척도를 맞추고 들어올림을 직접 더함)
```

`Unit_Hand_Offset.Place`가 `Transform.IsChildOf`로 **실제 부모를 보고**
분기합니다. 계층을 코드에 상수로 적어 두면 프리팹 배선이 바뀔 때
조용히 틀어지므로, 런타임에 판정하도록 했습니다.

## 8. 2차 정정 — 실측으로 잡은 두 가지 (y 부호 / 정렬)

7장까지 고쳤는데도 증상이 남았습니다. 추정을 멈추고 유닛을 실제로
만들어 월드 좌표를 찍어 봤습니다(`Hand_Runtime_Probe`).

### 8-1. y 부호가 반대였습니다 (핵심 원인)

실측값:

    몸통 월드 y = 0.29
    무기 월드 y = 0.23      <- 0.06 = 정확히 2px 아래

HUMAN 무기 오프셋이 `(-1, -2)`인데, 그 `-2`를 유니티에 그대로 넣어
**아래로** 2px 내려간 것입니다. 그런데 crawl에서 `-2`는 '위로 2px'을
뜻합니다. **좌표계가 반대**이기 때문입니다.

`tiletex.cc:122`:

```cpp
int pos_sy_adjust = ofs_y + inf.offset_y + size_oy;
// size_oy = TILE_Y - inf.height  -> 위에서 아래로 재는 값
```

crawl은 **화면 좌표계(y가 아래로 증가)**, 유니티 월드는 **y가 위로
증가**합니다. 그래서 `Weapon_Local`/`Shield_Local`에서 y에 음수를
곱합니다. **표의 값은 crawl 원본 그대로 두었습니다.** 뒤집기는 변환
지점에서만 하므로 원본 소스와 표를 그대로 대조할 수 있습니다.

수정 후 실측(`orc_orc_warlord`): 몸통·무기·방패의 bounds center y가
**셋 다 0.50**으로 일치합니다.

### 8-2. 좌우 반전은 상쇄하면 안 됩니다

실측에서 이런 값이 나왔습니다.

    몸통 월드 x 1.60 <- 무기 로컬 x -0.03 -> 무기 월드 x 1.63

음수 로컬이 **더 큰** 월드 좌표를 냈습니다. 부모(몸통) 스케일 x가
음수, 즉 좌우 반전 상태이기 때문입니다.

이것은 고칠 대상이 **아닙니다.** 병사가 왼쪽을 보면 손도 반대쪽에
있으므로 무기 보정도 함께 뒤집혀야 맞습니다. crawl 오프셋은 '오른쪽을
본 원본' 기준이고 반전은 그림 전체를 뒤집으므로, 보정이 같이 뒤집히는
것이 옳습니다. 상쇄했다면 왼쪽을 본 병사만 두 배로 어긋났을 것입니다.

### 8-3. 렌더링 정렬 (깜빡임 원인)

프리팹 실측 결과 세 스프라이트가 **전부 같은 레이어의 같은 순서**였습니다.

    Unit_Sprite  Unit(0)
    Unit_Weapon  Unit(0)
    Unit_Shield  Unit(0)

정렬 레이어와 순서가 모두 같으면 Unity는 다음 기준(카메라 축 거리)으로
순서를 정하는데, 세 스프라이트는 z가 사실상 같습니다. 그래서 어느 것이
앞에 올지가 **뒤집힐 수 있습니다.** 무기가 몸 뒤로 숨었다 나왔다 하는
현상이 그것입니다. 위치를 아무리 정확히 맞춰도 남는 문제입니다.

프로젝트에는 `Unit_Equipment` 레이어가 이미 정의되어 있었는데
**아무도 쓰지 않고 있었습니다.** 그 원래 의도대로 배선했습니다.

| 대상 | 레이어 | 순서 | 이유 |
|---|---|---|---|
| 방패 | Unit | -1 | 몸 뒤 (반대편 손) |
| 몸통 | Unit | 0 | 기준 |
| 무기 | Unit_Equipment | 0 | 몸 앞 |

무기만 레이어를 올린 이유: 9,600명이 겹치는 난전에서는 같은 레이어
안의 순서만으로 '내 무기가 남의 몸통 앞'이 보장되지 않습니다.

도구: **RTXX > 유닛 렌더링 정렬 설정** (`Unit_Sorting_Setup`)

## 9. 3차 정정 — 세로 보정을 쓰면 안 됩니다 (2px 오차)

8장 이후에도 **2px 정도**가 남는다는 보고가 있었습니다. 실측했습니다.

    [무기 몸통 대비] x 1.00 px, y 2.00 px

x는 표의 값(1px)이고 y도 표의 값(2px)입니다. **표대로 들어갔는데
그만큼이 오차로 보인다**는 뜻이므로, 값이 아니라 전제가 틀렸습니다.

### 원인 — ofs_y는 '잘린 타일'을 전제로 한 값입니다

crawl의 최종 위치 계산은 세 항의 합입니다.

```cpp
pos_sy_adjust = ofs_y + inf.offset_y + size_oy;   // tiletex.cc:122
```

| 항 | 의미 |
|---|---|
| `ofs_y` | 몬스터별 보정표 (우리가 이식한 것) |
| `inf.offset_y` | **잘라낸 양** ("texcoords may be smaller than orig image") |
| `size_oy` | `TILE_Y - inf.height`, 위쪽 정렬 |

우리는 타일을 자르지 않습니다(Full Rect + 하단 중앙 피벗). 그래서
뒤의 두 항이 0이고, **그림이 이미 캔버스 안 제자리에 있습니다.**

실측으로 확인한 결정적 증거:

    weapon_bow.png : 불투명 영역이 아래에서 3px 떠 있음

무기 타일은 캔버스에 **이미 띄워서** 그려져 있습니다. 여기에 `ofs_y`를
또 더하면 이중으로 올라갑니다. 그것이 보고된 2px입니다.

### 가로는 왜 그대로 두는가

좌우는 캔버스 중앙 정렬이라 잘림의 영향을 받지 않고, 실제로 손 위치
차이만큼만 필요합니다. 즉 **x는 유효하고 y만 무효**입니다.

### 수정

`Unit_Hand_Offset.buseVerticalOffset = false` (기본값)로 세로 보정을
끕니다. 표의 값은 crawl 원본 그대로 두었습니다 — 끄고 켜는 것은
변환 지점에서만 합니다.

수정 후 실측:

    [무기 몸통 대비] x 1.00 px, y 0.00 px   <- 세로 오차 해소
    [방패 몸통 대비] x 0.00 px, y 0.00 px

다시 켜야 할 상황: 타일을 잘라 쓰도록(Tight) 바꾸거나, 원본과 동일한
합성 파이프라인(`inf.offset_y` + `size_oy`)을 구현했을 때입니다.

## 10. 4차 — 무기 그립과 손의 세로 불일치 (인간 타일 고유 문제)

9장까지 고친 뒤에도 "무기의 쥐는 부분이 인간 유닛의 손과 Y축이 맞지
않는다"는 보고가 있었습니다. 이번에는 오프셋 계산 문제가 아니라
**그림 자체의 문제**였습니다.

### 실측 — 몸통마다 팔을 그린 높이가 다릅니다

PNG의 알파를 훑어 '팔이 가장 바깥으로 뻗은 행'을 손 높이로 봤습니다.
(타일 하단 기준, 클수록 위쪽)

| 몸통 | 손 높이 |
|---|---|
| `base_human_m` / `_f` (인형 베이스) | **y=15** |
| `orc_orc`, `orc_orc_warrior`, `orc_orc_warlord` | y=15 |
| `orc_orc_knight` | y=14 |
| `orc_orc_priest` | y=24 (지팡이 자세) |
| **`human_human`, `human_human2`, `human_human3`** | **y=19** |

`player/hand1`의 무기들은 **인형 베이스의 팔 높이(y=15)** 에 맞춰
그려져 있습니다. 오크는 우연히 같아서 맞았고, **인간 몬스터 타일만
팔이 4px 높게** 그려져 있어 무기가 손 아래에 남았습니다.

보고가 인간 유닛에 대해서만 나온 이유입니다.

### 수정

몸통별 손 높이 표(`handRow`)를 두고, 기준(15)과의 차이만큼 무기를
올립니다.

    보정 = (몸통 손 높이 - 15) px
    human_human -> (19 - 15) = +4px

**무기에만 적용합니다.** 방패는 반대편 팔에 들고 몸통에 붙어 있어
높이 편차가 작습니다. 함께 올리면 어깨 위로 떠 보입니다.

이 값을 런타임에 알파를 훑어 구하지 않는 이유: 텍스처를 읽기 가능하게
해야 하고(메모리 두 배) 9,600 유닛 생성 경로에서 그럴 이유가 없습니다.
그림이 바뀌지 않는 한 상수입니다.

### 검증

    [무기 몸통 대비] x 1.00 px, y 4.00 px   <- human_human2에 +4px 적용됨
    [방패 몸통 대비] x 0.00 px, y 0.00 px

### 이번 문제가 앞의 것들과 다른 점

| 장 | 원인 | 성격 |
|---|---|---|
| 7 | 계층(자식/형제)에 따른 변환 상속 차이 | 코드 |
| 8 | 정렬 레이어 미지정 | 설정 |
| 9 | ofs_y가 '잘린 타일' 전제 | 이식 오류 |
| **10** | **몸통 타일마다 팔 높이가 다름** | **그림 자체** |

앞의 셋은 계산을 고쳐 해결했지만, 이것은 crawl에도 해결책이 없습니다.
원본은 인간 몬스터 타일에 무기를 얹는 조합을 쓰지 않기 때문입니다.

## 11. 최종 정정 — 9장과 10장의 결론은 둘 다 틀렸습니다

사용자가 crawl 브랜치를 다시 제시해 재검증했습니다. 결과, 9장(세로
보정 폐기)과 10장(손 높이 보정 추가)의 결론이 **둘 다 잘못**이었습니다.

### 무엇이 틀렸나

**10장의 "crawl에도 해법이 없다"** — 사실이 아닙니다.
`tilemcache.cc:648`에 `TILEP_MONS_HUMAN`이 **명시적으로 등재**되어
있습니다.

```cpp
case TILEP_MONS_HUMAN:
case TILEP_MONS_HUMAN_1:
case TILEP_MONS_HUMAN_2:
    *ofs_x = -1;
    *ofs_y = -2;
```

그리고 `dc-mon.txt:752`의 `%sdir mon/humanoids/humans`가 이 타일이
우리가 쓰는 `human.png`임을 확인해 줍니다. crawl은 인간 몬스터 타일에
무기를 얹는 조합을 **정상적으로 지원합니다.**

**10장의 "인간 팔이 4px 높다"** — 잘못 읽은 것입니다.
알파를 훑어 '가장 바깥으로 뻗은 행'을 손으로 봤는데, 그 부분은
무기를 쥐는 손이 아니라 **반대편 팔**이었습니다.

**9장의 "세로 보정을 쓰면 안 된다"** — 이것도 틀렸습니다.
`inf.offset_y`와 `size_oy`가 0인 것은 맞지만, 그렇다고 `ofs_y`까지
버릴 이유는 없습니다. 남는 항이 바로 `ofs_y`입니다.

### 어떻게 확정했나 — 타일을 실제로 겹쳐 봤습니다

추론 대신 PNG를 디코드해 crawl과 같은 방식으로 합성했습니다.

```
ofs(-1,-2) 적용:              보정 없음:
  y18 ..WWWWW#####...         y18 .WWWW#######...
  y17 ...WWW####..###         y17 .WWWWW####..##
  y16 ....W#W##..####         y16 ..WWWWW##..###
  y15 ......W....####         y15 ...WWW.....###
  y14 .....WWW...####         y14 ....W.W....###
  y13 ......W...#####         y13 ......W...####
       ^ 손잡이 끝이                  ^ 손잡이가 팔
         팔에 물림                      아래로 내려감
```

`W`가 무기, `#`이 몸통입니다. **crawl의 값을 그대로 쓸 때** 단검
손잡이 끝이 팔에 정확히 물립니다.

### 최종 설정

| 항목 | 값 | 근거 |
|---|---|---|
| 가로 보정 | 표 그대로 | crawl 원본 |
| 세로 보정 | 표 그대로 (`buseVerticalOffset = true`) | 합성 검증 |
| y 부호 | 뒤집음 | crawl은 화면 좌표계(y 아래로 증가) |
| 손 높이 보정 | **제거** | 잘못된 측정에 기반했음 |

실측 확인:

    [무기 몸통 대비] x 1.00 px, y 2.00 px   <- 표의 (-1,-2)와 일치
    [방패 몸통 대비] x 0.00 px, y 0.00 px

### 교훈

같은 문제를 네 번 고치는 동안, 코드와 소스를 **읽고 추론한** 세 번은
모두 틀렸고 **그림을 직접 겹쳐 본** 마지막 한 번이 맞았습니다.
픽셀 단위 정렬 문제는 픽셀을 직접 보는 것이 가장 빠릅니다.

## 12. 적용 범위 점검

"모든 스프라이트에 보정치가 들어가 있는가"를 확인했습니다.

### 보정은 무기가 아니라 '몸통'에 대응합니다

먼저 짚을 것: 표의 키는 **몸통 스프라이트**이며, 무기·방패 종류별
값은 없습니다. 이것이 정상입니다. crawl도 같습니다.

```cpp
get_weapon_offset(m_mon_tile, &ofs_x, &ofs_y)   // 인자가 몬스터 타일뿐
```

무기 종류는 인자가 아닙니다. 즉 **한 몸통은 어떤 무기를 들든 같은
보정값**을 씁니다. 무기 7종 × 방패 3종에 대한 개별 값은 필요 없습니다.

### 점검 결과 (`Hand_Coverage_Probe`)

| 항목 | 개수 | 미등록 |
|---|---|---|
| 씬의 부대가 실제로 쓰는 몸통 | 8종 | **0** |
| 아직 안 쓰는 몸통 후보 | 2종 | **0** |
| 표에만 있고 실물이 없는 항목 | — | **0** |

등록된 몸통 10종:

```
human_human  human_human2  human_human3
orc_orc  orc_orc_warrior  orc_orc_knight  orc_orc_priest  orc_orc_warlord
base_human_m  base_human_f
```

세 방향(사용 중 / 후보 / 죽은 값)을 모두 봤고 빠진 것이 없습니다.

도구: **RTXX > 검증: 손 위치 보정 적용 범위**

몸통을 새로 추가하면 이 검사가 `[미등록]`으로 잡아냅니다. 런타임
경고보다 먼저 걸리므로 배선 직후에 한 번 돌리는 것이 좋습니다.

## 13. "몬스터 몸통 + 인형 무기" 조합이 원인 아닌가?

제기된 의문: 우리가 쓰는 human은 인형(`player/base`)이 아니라
**몬스터 타일**(`mon/humanoids/humans`)이다. 서로 다른 타일 집합을
섞어 쓰기 때문에 위치 오류가 나는 것 아닌가?

**타당한 의심이지만, 데이터가 반증합니다.**

### 섞어 쓰는 것은 맞습니다 — crawl도 그렇게 합니다

`tilemcache.cc:246-249`:

```cpp
m_mon_tile = tileidx_monster(mon) & TILE_FLAG_MASK;   // mon/ 계열
m_equ_tile = tilep_equ_weapon(*mon_weapon);           // player/hand1 계열
```

crawl 자신이 **몬스터 몸통에 인형 무기를 얹습니다.** 두 집합은 실제로
비율이 다릅니다(실측: 오크 팔 y13~16, 인간 몬스터 팔 y16~20).

**바로 그 차이를 흡수하려고 오프셋 표가 존재합니다.** 표가 몸통
타일별로 값을 갖는 이유가 이것입니다.

### 검증 — 몸통 6종에 무기를 겹쳐 봤습니다

`X`는 무기와 몸통이 겹치는 칸, 즉 손이 자루를 쥐는 지점입니다.

| 몸통 | 팔 높이 | 겹침(X) 위치 | 판정 |
|---|---|---|---|
| `human_human` | y16~20 | y16~20 | 일치 |
| `orc_orc` | y13~16 | y12~16 | 일치 |
| `orc_orc_warrior` | y13~16 | y12~16 | 일치 |
| `orc_orc_knight` | y11~15 | y11~15 | 일치 |
| `orc_orc_priest` | y14~19 | y14~19 | 일치 |
| `orc_orc_warlord` | y12~16 | y12~16 | 일치 |

**여섯 몸통 모두 각자의 팔 높이에서 무기를 쥡니다.** 팔 높이가 서로
4~5px씩 다른데도 그렇습니다. 표의 값이 그 차이를 정확히 상쇄하기
때문입니다.

### 결론

타일 집합이 다른 것은 사실이고 비율도 다르지만, **그것이 오류의
원인은 아닙니다.** crawl의 오프셋 표가 이미 그 목적으로 설계되어
있고, 우리는 그 값을 그대로 쓰고 있습니다.

(11장에서 제거한 `handRow` 보정이 바로 이 차이를 **두 번** 보정하려던
것이었고, 그래서 오히려 어긋났습니다)

## 14. 인간 타일만 원본값을 벗어납니다 (-2 → -4)

보고: "human_human 몸통에서 손잡이보다 살짝 위를 손이 잡고 있다."

**맞습니다.** 그리고 13장에서 "여섯 몸통 모두 일치"라고 한 제 판정은
너무 거칠었습니다. 겹치는 행이 있으면 일치로 봤는데, **무기의 어느
부위를 쥐는지**는 보지 않았습니다.

### 측정 방법을 바꿨습니다

'겹치는가'가 아니라 **'무기 타일의 어느 y를 쥐는가'** 를 역산했습니다.
무기의 자루(쥐는 부분)는 타일 기준 **y12~16**입니다.

| 몸통 | 쥐는 무기 부위 | 판정 |
|---|---|---|
| 인형 베이스 (설계 기준, ofs 0) | y12~16 | 자루 |
| 오크 (ofs -1) | y13~17 | 자루 |
| **인간 몬스터 (ofs -2, 원본값)** | **y18~22** | **칼몸** |

인간만 자루보다 6px 위, 즉 **칼몸을 쥐고 있습니다.**

원인은 이 타일의 팔 높이입니다. 인간 몬스터의 손은 y16~20인데
오크는 y12~16입니다. 무기는 인형 기준으로 그려져 있으므로 인간 쪽에서
더 큰 보정이 필요합니다.

### 값 선정

```
ofs_y   쥐는 무기 부위
  -2    y18~22   <- 칼몸 (crawl 원본)
  -3    y17~21
  -4    y14~18   <- 자루. 인형과 같은 관계
  -5    y13~17
```

`-4`를 택했습니다. 인형 베이스에 오프셋 0으로 얹었을 때와 같은
구조가 됩니다.

### crawl 원본과 다른 유일한 항목입니다

| 몸통 | 원본 | 우리 값 |
|---|---|---|
| `human_human` / `2` / `3` | (-1, **-2**) | (-1, **-4**) |
| 그 외 전부 | 원본 그대로 | 원본 그대로 |

crawl에서 이 조합이 왜 덜 어색해 보이는지는 확인하지 못했습니다.
(원본은 32px을 축소해 그리고, 몬스터가 무기를 든 조합 자체가 드뭅니다)
다만 우리 화면에서는 확대해 보므로 실측값을 따릅니다.

**표의 나머지 값을 임의로 바꾸지 마십시오.** 다른 몸통은 원본값이
정확합니다. 어긋나 보이면 먼저 '무기의 어느 부위를 쥐는지'를
측정하십시오.

### 설계상 주의

- **z는 건드리지 않습니다.** 앞뒤 순서는 `sortingOrder`가 정하므로
  여기서 z를 옮기면 그 규칙과 충돌합니다.
- **표에 없는 몸통은 경고를 남깁니다.** 몸통을 추가하고 표를 갱신하지
  않으면 조용히 어긋나므로, 그 상황을 눈에 띄게 만들었습니다.
- `base_human_m/f`는 값이 0인데 **표에 명시적으로 넣었습니다.**
  '빠뜨린 것'과 '실제로 0인 것'을 구분하기 위해서입니다.
- PPU를 32에서 바꾸면 `Unit_Hand_Offset.pixel`도 함께 바꿔야 합니다.
